## Causa de cada fallo
- **A) Acarreo de microsegundos.** `seconds_to_utc` calculaba `micros` y llamaba a
  `Utc.timestamp_opt(segundos, micros * 1000)` sin normalizar. Para `0.9999995`
  redondeaba a `1_000_000` µs, y `timestamp_opt` devuelve `None` con nanosegundos
  fuera de rango: de ahí la cadena vacía. Python hace el acarreo en
  `datetime._fromtimestamp` (`t += 1; us -= 1_000_000`).
- **B) Redondeo.** El port usaba `.round()` de Rust (mitad hacia fuera de cero);
  Python usa `round()`, que es *half-even*. Para `us = 999999.5` ambos coinciden
  por casualidad, pero no para otros valores (p. ej. `500000.5`).
- **C) Instantes negativos.** Python 3.12 en Windows convierte con
  `time.localtime` (ruta sin zona) y con `time.gmtime` (ruta UTC); el CRT de
  Windows rechaza la ruta local para cualquier `t < 0` y `gmtime` solo admite
  negativos hasta `-43200` (comprobado: `-43200` funciona, `-43201` da
  `OSError`). El port construía la fecha igualmente.
- **D) Falta `isoformat_millis_utc`.** No existía; es la forma que usa
  `agent/audit.py` para `ts` (siempre 3 decimales, truncando microsegundos).
- **E) `isoformat_utc`.** El formato ya era correcto (6 decimales solo con
  microsegundos ≠ 0 y `+00:00` siempre); se conserva y se cubre con fixtures.

## Arreglo
- `split_seconds` porta `datetime._fromtimestamp`: `trunc`, `round_ties_even`
  sobre el resto y acarreo a segundos.
- `local_datetime` devuelve `OSError: [Errno 22] Invalid argument` si
  `t < 0`; `utc_datetime` si `t < -43200`. `utc_instant` añade los textos de
  `nan` (`ValueError`) y de `±inf`/fuera de `time_t` (`OverflowError`), como
  Python 3.12.
- `isoformat_millis_utc` formatea `µs / 1000` con `{:03}` y `+00:00`.

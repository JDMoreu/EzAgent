## Decisiones
- `MenuEffects` extiende `SettingsEffects` (F6-06a): reutiliza `set_state`/`set_mic_muted` y añade `hang_up` (F6-03) y `kokoro_voices` (F6-04). Por omisión no hacen nada; F6-07 instala el cableado real. Se documenta en el encabezado del módulo.
- Los archivos se dividieron en `menu_wiring/menu.rs`, `apply.rs`, `apply/{live,mic,workers}.rs`, `tests.rs` y `tests/more.rs` porque el módulo y `apply.rs` superaban las 600 líneas tras `cargo fmt`.
- `AppEvent::TestDone` guarda el barge-in anterior como `0.0`/`1.0` porque la variante de F6-01 lo tipa `f64`; el manejo de F6-07 lo vuelve a leer con `bool(...)`. Es la única forma de conservar el dato sin tocar F6-01.
- `apply_instant_setting`, `cfg.save()` y `_save_from_menu` escriben en el `config_file` de la instancia, no en `config_path()`, siguiendo F6-06a/F6-01. Un fallo de `save_key` se registra y no propaga.
- `_hud_menu_settings` siempre devuelve `Some`: el Python devuelve `None` si falla un `import`, que en Rust no existe. Un fallo al leer `llm.json` solo se registra, como el `except` del Python.
- `MenuEffects::kokoro_voices` devuelve vacío por omisión (no validar): `SpeakerApi` de F6-01 no expone el diccionario de voces cargado de Kokoro. La rama de validación está probada con un grabador que sí devuelve voces; F6-07 puede implementar el método con las voces reales.
- `_restart_whisper_async`: `ensure_whisper` de Rust devuelve `Option` y no lanza, así que el `log("No pude reiniciar whisper-server: …")` del `except` de Python no tiene ruta en este puerto.
- `setting_float` usa el parser de Rust; no se portan los guiones bajos numéricos (`float("1_000")`) porque el menú nunca los envía.
- El hilo de refresco de dispositivos al abrir el menú se llama `ezagent-devices` (Python no lo nombra); coincide con el nombre que ya usa F6-01 al arrancar.
- `_reload_mic` convierte un índice negativo de Python a `None` (Rust no tiene `Option<usize>` negativo); el comportamiento posterior es el mismo (`pick_input_device` elige el predeterminado).

## Rarezas del Python reproducidas
- `_apply_settings` llama a `_apply_turn_settings()` **antes** de `_reload_mic`; al cambiar de dispositivo, el `MicCapture` nuevo nace con `turn_detector=None` y Smart Turn queda apagado hasta el siguiente ajuste. Se reproduce tal cual (no se corrigió).
- `_test_voice_from_menu` deja `cfg.barge_in=False` y solo lo restaura al manejar `test_done`; si ese evento no se procesa (F6-07 aún no cableado), el ajuste queda apagado. Se reproduce.
- `_apply_settings` valida la longitud de `llm_profile_name` con `or ""` pero luego escribe `str(values.get(...)).strip()`; un valor `None` se convierte en `"None"`. Se reproduce.
- `_hud_menu_settings` lanza un hilo de refresco de dispositivos cada vez que se abre el menú con la caché vacía. Se reproduce.

## Pendiente o riesgos
- La validación de voces de Kokoro queda inactiva en la app real hasta que F6-07 (o una ampliación de `SpeakerApi`) exponga las voces cargadas mediante `MenuEffects::kokoro_voices`. La rama está probada con dobles.
- `hang_up` y `set_state` son no-op por omisión: al cambiar dispositivo durante una llamada, `finish_call` reprograma `start_call`, pero `in_call` sigue activo hasta que F6-07 instale la costura real; `start_call` entonces no arranca. Es el mismo estado provisional que dejó F6-06a con `set_mic_muted`.
- `_restart_whisper_async` no puede registrar el error de `ensure_whisper` porque la API de Rust no lo devuelve; si F6-07 necesita ese aviso, `ez-stt` debería exponer un `Result`.
- Las pruebas no ejercitan una escritura real de `llm.json` al cambiar de proveedor: `save_provider_profile` usa la ruta de fábrica, como el Python, y se evita tocar el archivo del usuario en pruebas. La rama queda cubierta por las pruebas de `ez-core`.
- `cargo clippy --workspace --all-targets` no se ejecutó completo; la puerta del brief pide `-p ez-app`. `cargo test -p ez-app` y `cargo fmt --all` sí se ejecutaron.

## Decisiones
- `llm_request`: cada turno usa el `Messenger` real y un `http.server` en `127.0.0.1` (puerto efímero). Solo se guardan `path` y el cuerpo JSON parseado; el puerto y las cabeceras (incluida la sesión aleatoria de `opencode`) no forman parte del oráculo.
- `llm_request`: `time.monotonic` se congela en `1000.0` para que `last_rounds` («0 ms al 1.er fragmento») sea reproducible.
- `llm_sse`: el servidor local escribe la respuesta entera, por líneas o byte a byte (`delivery`) para fijar los cortes en mitad de línea; `cut_at` corta el flujo a mitad de evento.
- `llm_sse`: los errores esperados del SDK se registran con `add_error` y el texto exacto de Python (`APIError`, `AuthenticationError`, `RateLimitError`, `JSONDecodeError`, `RuntimeError`). El generador falla si un caso normal lanza.
- `llm_tools`: el cliente guionizado imita `tests/test_messenger.py`; los guiones se serializan en la entrada (`scripts`) para que el caso se pueda reconstruir sin objetos Python. `time.monotonic` se congela en `1000.0`.
- `llm_tools`: los casos de error previstos se marcan con `expect_error`; cualquier otra excepción aborta la generación.
- `parity/gen/manifest.json` no se tocó; la integración del manifiesto la hace el orquestador.
- No se tocó `rust-migration/python-quirks.md` porque el brief limita los archivos; las rarezas observadas quedan en «Pendiente o riesgos».

## Pendiente o riesgos
- Rareza del Python: `_status_of` busca el substring `" 429"`, así que
  `"Error 4290"` se clasifica como 429 (caso incluido). El puerto Rust debe
  reproducirlo si quiere paridad exacta.
- Rareza del SDK de OpenAI (3.44.0): `SSEDecoder` conserva `last_event_id`; un
  `id:` seguido de líneas en blanco produce eventos con `data` vacía y
  `json.loads("")` lanza `JSONDecodeError`. Se dejó `id:` fuera de los casos
  válidos; si se sube el SDK, hay que regenerar los fixtures de `llm_sse`.
- Los errores de `llm_sse` incluyen clases internas del SDK (`APIError`,
  `AuthenticationError`, `JSONDecodeError`). El puerto Rust devuelve `LlmError`
  con otro texto; la paridad debería comparar el texto amigable/estado, no el
  nombre de la clase Python.
- `_open_stream` registra «Reparé 0 llamada(s)» en el reintento porque el turno
  ya saneó el historial antes de abrir el stream; el caso fija el reintento,
  no el contador del log.
- La compactación de contexto deja solo el turno nuevo en `recent` porque el
  mensaje del usuario se añade antes de `fit_recent`; el fixture lo captura tal
  cual (dos peticiones de dos mensajes cada una).
- Los tiempos de `last_rounds` se fijan en `0 ms` con el reloj monótono
  congelado; la latencia real no es parte del oráculo.
- El caso `note_done` de salida larga pesa ~12 KB a propósito para fijar el
  recorte a 12.000 caracteres.

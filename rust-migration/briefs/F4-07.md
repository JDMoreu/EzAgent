## Notas específicas
- Reutiliza lo ya integrado en `ez-llm`: `openai.rs`/`anthropic.rs`/`sse.rs`/`errors.rs` (F4-06: lee su API pública y su informe `rust-migration/reports/F4-06-r1.md`), y `tool_json.rs`, `tool_markup.rs`, `context.rs`, `condenser.rs` (F3-01). Usa también `ez_core::llm_providers` y `ez_core::config::VoiceConfig`.
- **Dependencia circular a evitar:** `ez-agent` depende de `ez-llm`, así que `ez-llm` NO puede depender de `ez-agent`. En el Python `Messenger` recibe un `runtime` del agente (`AgentRuntime`) y lo llama (esquemas de herramientas, `execute`, prompt del sistema, memoria, límites de herramientas por turno…). Define en `messenger/mod.rs` un `pub trait AgentRuntimeApi` (o el nombre que prefieras) con exactamente los métodos que el Messenger usa del runtime, con tipos de `serde_json::Value`/`String`, documentado con el método Python equivalente. F4-09 lo implementará en `ez-agent`. Anota la lista completa de métodos en el informe.
- Concurrencia: el Messenger se usa desde varios hilos (turno de voz, UI de chat, cancelación). Estado compartido con `Mutex`/`RwLock`; el `RLock` del historial del Python se modela con un `Mutex` y secciones críticas cortas. `ask_stream` devuelve un iterador de fragmentos de texto (`impl Iterator<Item = String>` o una estructura propia que implemente `Iterator`), cancelable con `cancel_turn` desde otro hilo (`TurnToken` con `AtomicBool`). Nada de async.
- Los textos que el Messenger genera (avisos de herramientas lentas, de espera, de recorte de contexto, errores amistosos) van **literales** del Python.
- El módulo `messenger/mod.rs` y cada submódulo deben respetar las 600 líneas: divide en subcarpetas si hace falta (por ejemplo `messenger/request/stream.rs`). El archivo `messenger/notices.rs` NO es tuyo (F4-09).
